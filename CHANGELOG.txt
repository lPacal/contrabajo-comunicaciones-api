❚❙❘ VERSION 0.4.0-Pre-Alpha
⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺
├─• Nuevo endpoint `PATCH /api/chats/{idChat}/desactivar` — cierra un chat por su ID; accesible por cualquier participante (cliente o trabajador).
├─• `desactivarChat` (por oferta+trabajador) relajado: ambos participantes pueden cerrar el chat; ya no es exclusivo del cliente.
├─• Mensaje de sistema cifrado `"El chat fue finalizado."` insertado automáticamente al cerrar un chat por cualquier vía.
├─• Evento WebSocket `CHAT_CERRADO` emitido a ambos participantes (`/topic/chat/{id}`) al desactivar un chat, para sincronizar la UI en tiempo real.
├─• `iniciarChat` ahora reutiliza solo chats ACTIVOS; si el chat anterior fue cerrado, se crea uno nuevo en lugar de reabrir el cerrado.
├─• `ChatOfertaRepository`: nueva query `findTopByIdTrabajadorAndIdClienteAndIdOfertaServicioAndActivoTrueOrderByIdDesc` para búsqueda del chat activo más reciente.
├─• `crearNuevoChat` extraído como método privado para eliminar duplicación entre `iniciarChat` y futuros flujos de reapertura.
├─• `MensajeChatRequestDTO`: campo `tipo` opcional añadido (0 = normal, 1 = sistema) para retrocompatibilidad con clientes anteriores.
├─• `ChatOferta`: campo `idCita` eliminado del modelo JPA — la vinculación de cita se gestiona desde `servicios_api`.
├─• `pom.xml`: versión explícita de Lombok (`1.18.44`) fijada en `annotationProcessorPaths` para evitar conflictos de compilación con el processor de Maven.
└─• Helper privado `emitirEventoChatCerrado` centraliza la emisión del evento WebSocket de cierre para ambos participantes.

->>> Implementar reapertura controlada de chat cerrado con nuevo hilo de mensajes.
->>> Exponer GET /api/chats/{idChat} para obtener detalle de un chat por ID.


❚❙❘ VERSION 0.3.0-Pre-Alpha
⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺⎺
├─• Nuevo endpoint WebSocket nativo `/ws-comunicaciones-native` (STOMP puro sin SockJS) para clientes Android/iOS junto al endpoint SockJS existente.
├─• Nuevo endpoint GET `/api/chats` — devuelve el listado de chats del usuario autenticado como `ChatResponseDTO`.
├─• Nuevo endpoint PATCH `/api/chats/{idChat}/vincular-cita` — asocia una cita creada en `servicios_api` al chat correspondiente.
├─• Nuevos DTOs: `ChatResponseDTO` (listado de chats) y `VincularCitaDTO` (payload de vinculación de cita).
├─• `ChatCryptoService`: cifrado AES/GCM con prefijo `ENCv1` para todos los mensajes nuevos; desencriptado transparente hacia el cliente con compatibilidad hacia históricos en claro.
├─• `ChatService` refactorizado: cifrado integrado en el guardado de mensajes, retrocompatibilidad de metadata en chats pre-existentes, `listarChatsUsuario` y `vincularCita`.
├─• Mensaje de sistema automático al iniciar un chat nuevo: notifica al trabajador vía WebSocket que un cliente está interesado en su servicio.
├─• `ChatOferta`: 4 nuevos campos de visualización desnormalizados (`id_cita`, `username_trabajador`, `username_cliente`, `titulo_servicio`) para evitar joins cross-microservicio al listar chats.
├─• `MensajeChat`: nuevo campo `tipo` (0 = normal, 1 = sistema) para diferenciar mensajes de usuario de los generados automáticamente por el backend.
├─• `ChatRequestDTO`: extendido con `usernameTrabajador`, `usernameCliente` y `tituloServicio` para poblar metadata del chat al iniciarlo.
├─• `MensajeChatRepository`: nuevas queries para marcado masivo de mensajes como recibidos y leídos.
├─• `Reporte`: campos `resolucion_reporte` (VARCHAR 50) y `resuelto` (boolean, default false) para seguimiento de moderación.
├─• [BD] `chat_oferta`: nuevas columnas `id_cita INT NULL`, `username_trabajador VARCHAR(100) NULL`, `username_cliente VARCHAR(100) NULL`, `titulo_servicio VARCHAR(200) NULL`.
├─• [BD] `mensaje_chat`: nueva columna `tipo TINYINT NOT NULL DEFAULT 0`.
└─• [BD] `reporte`: nuevas columnas `resolucion_reporte VARCHAR(50) NULL` y `resuelto BIT NOT NULL DEFAULT 0`.

->>> Implementar paginación en GET /api/chats y en el historial de mensajes.
->>> Conectar módulo de Reportes con endpoints de resolución para flujo de moderación completo.
->>> Reemplazar cifrado backend por E2EE real cuando se definan claves por cliente.
